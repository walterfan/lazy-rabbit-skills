# Sandbox Security: Enforcement, Not Decoration

A `sandbox.config.yaml` the runtime ignores protects no one. This note maps each
guardrail to how it is actually enforced, and lists the threats each one stops.

## The threat model in one paragraph

You are letting strangers run arbitrary code on your infrastructure. Assume some
of them are hostile and some are merely careless. Without limits, a sandbox is:
a crypto miner (unbounded CPU), a DoS amplifier (unbounded egress), a data
exfiltration hop (open network), a host-filler (unbounded disk), or a
resource-starve on your other tenants (no caps). The guardrails exist to make
each of those impossible, not merely discouraged.

## The three mandatory guardrails

### 1. Timeout — stop runaway execution
- **Stops:** infinite loops, hangs, slow-loris style stalls, "mine forever".
- **Enforce:** wrap the process in `timeout <N>` (as `run.sh` does) AND set an
  orchestrator-level `max_session_minutes`. Belt and suspenders.

### 2. Resource caps — no starving the host
- **Stops:** CPU mining, memory bombs, fork bombs, disk fill.
- **Enforce:** `--cpus`, `--memory`, `--pids-limit`, and a size-bounded
  `--tmpfs` for scratch. On Kubernetes: `resources.limits` + an ephemeral-storage
  limit. A memory limit without a pids limit still allows a fork bomb — set both.

### 3. Network egress allowlist — default deny
- **Stops:** the sandbox becoming a DoS source, an exfil hop, or a scanner.
- **Enforce:** this is the one people fake. `--network sandbox-net` alone does
  nothing unless that network is actually restricted. Real options:
  - an `--internal` Docker network plus an egress proxy that only forwards to the
    allowlisted hosts;
  - Kubernetes `NetworkPolicy` with an explicit egress allowlist (and a
    default-deny policy in the namespace);
  - firewall/iptables rules on the sandbox network limited to the API hosts.
  Allow only the API's own hosts and its OAuth token/authorization endpoints —
  nothing else, DNS included (pin it).

## Additional hardening (cheap, generated by default)

| Control | Flag | Stops |
|---|---|---|
| Non-root user | `--user 1000:1000`, `USER` in Dockerfile | privilege escalation, host-file writes |
| Read-only root fs | `--read-only` + `--tmpfs /tmp/work` | tampering, persistence between runs |
| Drop capabilities | `--cap-drop ALL` | raw sockets, mount, ptrace tricks |
| No new privileges | `--security-opt no-new-privileges` | setuid escalation |
| Ephemeral | `--rm`, destroy after session | cross-session data leaks |

## Secrets: the token never lives in the box

- The image is built with **no** token (see the Dockerfile — nothing is copied in
  but code and deps).
- The token is injected at **run** time via `--env ACCESS_TOKEN`, sourced from an
  OAuth2 broker or the learner's own key. It is short-lived and rotatable.
- It is never logged, never printed, never written to the read-only image.
- If a learner pastes a real long-lived key into a cell, treat it as compromised:
  tell them to rotate it and move to env injection.

## Common ways people fake a sandbox (don't)

- **"It's in a container, so it's sandboxed."** A container with host networking,
  root, and no caps dropped is barely a speed bump.
- **`--network none` then giving up.** The tutorial needs to reach the API; the
  answer is an *allowlist*, not "no network" or "all network".
- **CPU/mem limits but no pids limit.** Fork bomb still wins.
- **A config file with limits that `run.sh` never applies.** Decoration. The
  config and the run command must agree — Verification checks this.
- **Baking a "demo" key into the image "just for the sandbox".** That key leaks
  the moment the image does. Inject at run time.

## Kubernetes note

If you run sandboxes on K8s instead of raw Docker, translate the same controls:
`activeDeadlineSeconds` (timeout), `resources.limits` + ephemeral-storage
(caps), a default-deny `NetworkPolicy` with an egress allowlist (network),
`securityContext` with `runAsNonRoot`, `readOnlyRootFilesystem`,
`allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`, and a short-lived
Job that is deleted after the session. For stronger isolation between tenants,
consider gVisor or Kata Containers.
