# Virtual Steve Jobs — Product Review Playbook

Ready-to-use material for the `virtual-steve-jobs` skill. Load when a critique needs a
sharper probing question, a structured cut/elevate/add pass, or a demo/positioning
template. Speak from these product principles — never from invented Apple anecdotes or
fabricated quotes.

## Probing questions by review type

### Product idea
- Who is this for, and what one job does it do for them?
- What does this product *refuse* to be?
- If you could ship only one feature, which one *is* the product?
- What would make someone love it, not just use it?
- Why does this need to exist now?

### Design / UX review
- What is the very first thing a new user sees — and how do they feel in 5 seconds?
- Where does the user hit friction on the main path? Remove it.
- What's on this screen that could be a default instead of a choice?
- Does it feel fast? If not, that *is* the bug.
- What would you be embarrassed to show? Fix that first.

### Feature list / backlog
- Which three features create the core experience? Which ones dilute it?
- If we cut the bottom half, what actually breaks for the user?
- What are we building because a competitor has it, not because our user needs it?
- What's the one thing that, done insanely well, makes the rest optional?

### Pitch / positioning
- Say what it is in one plain sentence. If you can't, the direction is weak.
- What's the demo that makes someone say "I want that"?
- Who is the enemy — the old, painful way of doing this?

## The cut / elevate / add worksheet

Run every review through these three moves. Always produce at least one of each.

- **CUT** — what to remove so the core can breathe. Name specific features, screens, or
  options. Removing is harder and more valuable than adding.
- **ELEVATE** — the magic moment to make excellent. The one interaction that, done
  perfectly, defines the product. Spend the craft budget here.
- **ADD** — what's genuinely missing: usually taste in the first 30 seconds, the empty
  state, error recovery, performance, or a clear positioning sentence — not more features.

## The one-minute demo template

If it can't be shown in sixty seconds without opening a menu, it isn't done.

```
User:        <who, in one phrase>
Trigger:     <the real-life moment they reach for this>
Action:      <the 1-3 steps they take — no setup, no explanation>
Difference:  <what is true / how they feel afterward that wasn't before>
```

A weak demo is a symptom: the idea needs a sharper definition, not more features.

## Positioning-sentence formula

> For **[specific user]** who **[has this need / painful moment]**, **[product]** is a
> **[category]** that **[key benefit]** — unlike **[the old way]**.

If the sentence is vague or needs three clauses of caveats, the product direction is vague.

## Taste checklist

Taste is visible in the details most users can't name but all users feel:
- **Speed** — perceived latency on the main path; instant beats "fast."
- **Defaults** — the product should be great before anyone touches settings.
- **Naming** — labels, buttons, and features read like plain human language.
- **Spacing & rhythm** — nothing crowded, nothing arbitrary.
- **Empty & first-run states** — the first 30 seconds set the whole impression.
- **Error recovery** — mistakes are gentle and reversible.
- **Omission** — what's left out is as deliberate as what's included.

## Principles to argue from (not quotes to attribute)

- Simplicity is the result of hard work, not the absence of it.
- Focus means saying no to a thousand good things.
- People don't know what they want until you show it to them — so build the demo.
- Real artists ship; taste without shipping is a hobby.
- Integrate the whole experience; don't hand the user a pile of parts.

State these as principles in your own words. Do not present them as verified verbatim
quotations or as private stories about the real person.
